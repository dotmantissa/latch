# P0 runtime and live feasibility

Application implementation follows the prerequisite order in [the roadmap](IMPLEMENTATION.md).
This step provides runtime scaffolding and executable probes. It does not establish buyer fit,
model correctness, isolation or a working purchase workflow.

## Local setup

Run `bash scripts/bootstrap.sh` from a fresh checkout. It installs pinned Node and Python
runtimes under ignored `.tools`, installs the exact locked dependency graphs, and checks the
linked SQLite library on an actual temporary database. It does not initialize Git, provision
a cloud machine, install a browser or call inference. Linux is the intended deployment host.
The bootstrap needs an existing `python3` with pip and npm to install the pinned tools.

The required versions are Node 24.22.2 and Python 3.13.18. TypeScript 5.9.3 satisfies the
OpenAPI generator's current peer requirement. The installed Python links SQLite 3.53.1,
which includes the required WAL fix. The runtime check rejects SQLite before 3.51.3 before
opening storage. The system Python and an independently installed SQLite wheel are not
assumed to meet this requirement.

```bash
bash scripts/latch.sh runtime
.venv/bin/pytest
.venv/bin/ruff check services tests
```

These tests exercise policy boundaries and actual local SQLite. They do not use a network
mock or claim a successful live supplier task. No frontend application is present yet.
Frontend dependencies are locked for the later authorized packages.

## Real source input

Set `LATCH_SOURCE_TASK_FILE` to a consented private JSON document matching
[the generated task schema](../infra/source-task.schema.json). Do not copy the historical
synthetic scenario into this document. The input needs the actual buyer's three required
items, quantities, USD budget, deadline with timezone, delivery basis and one to three
public supplier URLs. Profiles name exact reviewed origins and offer paths, main content
selectors, optional terms pages and expiry. No supplier is admitted by default.

Confirm with the buyer that the task is genuinely compatible with public HTML, and obtain
capture and inference consent. A successful HTTP response is insufficient proof of source
completeness or permission. Private portals, PDF, login, token URLs and unsupported delivery
interpretations remain outside this gate.

```bash
bash scripts/latch.sh source
```

This command validates input and profile admission only. It records `input_validated`, not
live source fit. An independent person must inspect actual captures and verify exact item,
quantity basis, stock, tax, shipping and delivery support. Missing essential terms must be
recorded as unsupported. Do not alter a live supplier page to manufacture a passing case.

## Vultr capability checks

Configure `LATCH_MODEL_ID` from the actual Vultr catalog and `LATCH_INFERENCE_KEY_FILE`
as an owned credential file with mode 0600. The provisioning token and inference token
are different credentials. Never supply either in an argument, source file or frontend
environment variable. The client supports only `https://api.vultrinference.com/v1`.

Once an actual admitted source capture has been produced on the isolated worker:

```bash
bash scripts/latch.sh model --capture var/p0/capture.json
```

This makes at most three actual provider calls: JSON text output, a bounded tool schema,
and screenshot input. It requires real usage counters, applies time and output limits,
does not execute arbitrary returned instructions, and has no alternate provider. Screenshot
transcription remains a proposal requiring independent source review. Only the public image
goes to the vision request; buyer identity, budget and credentials do not.

## Recovery and gate inventory

Reports are written atomically with mode 0600 under the ignored `var/p0` directory.
The local runtime report can be shared after review; buyer documents, captures and model
outputs remain private. Raw exception details and provider bodies are omitted from CLI
errors. A rerun replaces only its named probe report.

```bash
bash scripts/latch.sh gate
```

The inventory deliberately returns a pending result until the live evidence is reviewed.
It is not an automated authorization to start P1. Complete source compatibility, actual
Vultr usage, browser isolation, allowed and denied networking, timeout and cleanup before
updating the recovery checklist and proceeding. Do not treat unit policy checks as proof
that the worker enforces them.
